# ติดตั้ง Clinical Pharmacist v5

สถานะ: ชุดสำหรับทดสอบและตรวจรับ ไม่ใช่การรับรองความแม่นยำทางคลินิก

## 1. สำรองของเดิมและเตรียมพื้นที่ทดสอบ

1. เก็บ deployment เดิมไว้ และสำรองโค้ด Apps Script เดิม
2. แนะนำสร้าง Apps Script โปรเจกต์ทดสอบแยกก่อน เพื่อไม่ทำให้หน้าเว็บรุ่นเก่าเสียการเชื่อมต่อ
3. รุ่นเก่าใน GitHub อ้างอิง commit `6eb17bd1cde4cef9ead160c3197e6d6905fc6f80`
4. ทดสอบด้วยข้อมูลจำลอง ไม่ใส่ชื่อ HN หรือข้อมูลผู้ป่วยจริง

## 2. เตรียม Apps Script

1. เปิด Apps Script → สร้างโปรเจกต์
2. ใส่เนื้อหา `apps-script/Code.gs` ลงไฟล์ `Code.gs`
3. สร้างไฟล์สคริปต์ชื่อ `Core` แล้วใส่เนื้อหา `apps-script/Core.gs`
4. Project Settings → เปิดแสดง manifest `appsscript.json` แล้วแทนที่ด้วยไฟล์ manifest ที่ให้มา
5. ไม่ต้องสร้าง `Index.html` ใน Apps Script รุ่นนี้ หน้าเว็บทำงานที่ GitHub Pages
6. ลบฟังก์ชันรุ่นเก่าที่เหลือในโปรเจกต์ทดสอบ โดยเฉพาะ `getApiKey()` เพื่อไม่ให้ยังเรียกได้จากภายนอก

## 3. เตรียมฐานบันทึกและทะเบียนหลักฐาน

สร้าง Google Spreadsheet ใหม่ที่บัญชีผู้ deploy แก้ไขได้ ให้สิทธิ์เฉพาะผู้รับผิดชอบ ไม่เปิดลิงก์สาธารณะ

คัดลอก Spreadsheet ID จาก URL ช่วง `/d/…/edit` ไปใส่ Script Properties ชื่อ `AUDIT_SPREADSHEET_ID`

เมื่อเชื่อมต่อครั้งแรก ระบบจะสร้างชีท:

- `Audit`: เวลา รหัสผู้ใช้ คำสั่ง request ID สถานะ digest และรุ่นระบบ ไม่มีข้อความเคสในแต่ละแถว
- `References`: ทะเบียนหลักฐานที่หน่วยงานตรวจทานเอง

ห้ามเปลี่ยนชื่อหัวตาราง References:

| คอลัมน์ | สิ่งที่ต้องใส่ |
| --- | --- |
| id | รหัสไม่ซ้ำ เช่น `LOCAL_AMOX_01` ใช้อักษรอังกฤษ ตัวเลข `_` หรือ `-` |
| title | ชื่อเอกสารจริง |
| url | URL HTTPS ของต้นทางที่ผู้ตรวจเปิดตรวจได้ |
| version | รุ่น/ปี/ฉบับจริง |
| reviewedBy | ผู้รับผิดชอบที่อ่านและตรวจเนื้อหาแล้ว |
| reviewedAt | วันที่ตรวจ YYYY-MM-DD ตั้งเซลล์เป็น Plain text |
| expiresAt | วันทบทวนครั้งถัดไป YYYY-MM-DD ตั้งเซลล์เป็น Plain text |
| scope | ยา ข้อบ่งใช้ formulation กลุ่มอายุ และบริบทที่ใช้ได้ |
| excerpt | ข้อความที่มีสิทธิ์ใช้และผู้ตรวจยืนยันแล้ว ไม่เกิน 8,000 ตัวอักษรต่อฉบับ |
| active | `TRUE` เพื่อเปิดใช้ หรือ `FALSE` เพื่อถอน |

อย่าใส่ข้อความทั้งบทจากฐานข้อมูลที่ไม่มีสิทธิ์คัดลอก และอย่าใส่ข้อมูลระบุตัวผู้ป่วยในทะเบียนหลักฐาน

ระบบไม่ได้เข้าถึง Lexicomp/UpToDate โดยอัตโนมัติ ไม่มีฐานข้อมูลยาที่รับประกันครอบคลุมทุกยา การเลือกเอกสารและความถูกต้องของ excerpt เป็นความรับผิดชอบของหน่วยงาน

## 4. สร้างผู้ใช้รายบุคคล

1. เปิด `setup.html` จากหน้า GitHub Pages หรือ localhost
2. ใส่รหัสผู้ใช้ ชื่อผู้ตรวจ และบทบาท
3. กดสร้างกุญแจ ระบบสุ่ม 256 บิตด้วย Web Crypto ในเครื่อง
4. ส่งกุญแจ 64 ตัวอักษรให้เจ้าของบัญชีผ่านช่องทางส่วนตัว และเก็บใน password manager
5. คัดลอก JSON ที่มีเฉพาะ `keyHash` ไปใส่ Script Property `USERS_JSON`
6. เพิ่มผู้ใช้ใหม่โดยเพิ่ม object ใน array เดิม ห้ามเขียนทับผู้ใช้อื่น
7. ถอนสิทธิ์โดยตั้ง `active:false` หรือเอารายการผู้ใช้ออก เปลี่ยนกุญแจโดยสร้างใหม่แล้วแทน keyHash

ห้ามใส่ `GEMINI_API_KEY`, กุญแจผู้ใช้ หรือ `USERS_JSON` จริงใน GitHub / README / chat

ระบบนี้ใช้กุญแจผู้ใช้สำหรับกลุ่มทดสอบที่ควบคุมได้ ยังไม่ใช่ SSO/MFA หรือระบบตัวตนของโรงพยาบาล ผู้มีสิทธิ์แก้ Script Properties และ Spreadsheet ถือเป็นผู้ดูแลที่เชื่อถือได้

## 5. Script Properties ที่ต้องตั้ง

| ชื่อ | ค่า |
| --- | --- |
| GEMINI_API_KEY | คีย์ Gemini ของหน่วยงาน |
| GEMINI_MODEL | เริ่มทดสอบด้วย `gemini-3.5-flash-lite` หรือโมเดลที่บัญชีรองรับ โดยต้องทดสอบใหม่เมื่อเปลี่ยน |
| USERS_JSON | Array ผู้ใช้ที่ได้จาก setup.html |
| AUDIT_SPREADSHEET_ID | ID ของ Spreadsheet ที่เตรียม |
| AI_ENABLED | เริ่มด้วย `false`; เปลี่ยนเป็น `true` หลังตรวจการอนุญาตส่งข้อมูลและ quota/billing ของบัญชี |
| CLINICAL_RELEASE_APPROVED | เริ่มด้วย `false`; เปลี่ยนเป็น `true` หลังผู้รับผิดชอบเซ็นรับ UAT เท่านั้น |

การตั้งค่า release เป็น true เป็นเพียงการปลดล็อกตามการตัดสินใจของหน่วยงาน ไม่ได้ทำให้โมเดลผ่านการรับรองหรือรับประกันคำตอบอัตโนมัติ

หาก API key เดิมเคยเปิดเผยผ่าน getApiKey() ควรเปลี่ยนคีย์หลังปิดช่องโหว่

## 6. Deploy backend

1. Deploy → New deployment → Web app
2. Execute as: บัญชีเจ้าของที่มีสิทธิ์เปิด Spreadsheet และใช้ Gemini
3. การเรียกตรงจาก GitHub Pages ต้องให้ endpoint รับคำขอจากผู้ใช้หน้าเว็บได้ ระบบ v5 ตรวจสิทธิ์ซ้ำด้วยกุญแจรายบุคคลภายใน `doPost`
4. หากนโยบาย Google Workspace ไม่อนุญาตการเข้าถึงลักษณะนี้ ห้ามพยายามข้ามนโยบาย ให้ใช้ gateway/SSO ที่หน่วยงานอนุมัติ
5. อนุญาต scopes ที่แสดง และคัดลอก URL `/exec` ไม่ใช้ `/dev`
6. ทุกครั้งที่แก้โค้ดให้ deploy เวอร์ชันใหม่ด้วย การกด Save อย่างเดียวไม่อัปเดต deployment ที่เผยแพร่

## 7. เปิดหน้าเว็บบน GitHub Pages

1. นำไฟล์ชุด v5 เข้า branch ทดสอบ/PR ก่อน
2. เมื่อจะเผยแพร่ ต้องมี `index.html`, `app.js`, `core.js`, `styles.css`, `setup.html`, `setup.js` อยู่ในโฟลเดอร์ที่ Pages ใช้
3. GitHub → Settings → Pages ใช้แหล่งเผยแพร่เดิมของ repository
4. เปิดหน้าเว็บ → เชื่อมต่อ / ผู้ใช้ → ใส่ URL `/exec` รุ่นใหม่ รหัสผู้ใช้ และกุญแจ
5. ต้องแสดง v5.0.0-rc1 ตรงทั้งสองฝั่ง ถ้าไม่ตรงระบบจะปฏิเสธ
6. ตรวจว่า health แสดงฐานบันทึกตั้งค่าแล้ว และเลือกเอกสารจากทะเบียนได้
7. เปิด AI สำหรับข้อมูลจำลอง ทดสอบส่งจริงจากเบราว์เซอร์ ต้องเห็น JSON response และ audit ครบ ห้ามใช้ `mode:no-cors` เพราะจะอ่านผลตอบกลับไม่ได้

## 8. การตรวจรับก่อนใช้กับผู้ป่วย

ทำรายการใน `CLINICAL_UAT.md` และบันทึกผลจริงลง `VALIDATION.md` ของหน่วยงาน ต้องทดสอบทั้งร้านยาและ workflow โรงพยาบาลที่ต้องการใช้ ไม่เปิดทุกยา/ทุก ward โดยอัตโนมัติ

ฉลากที่รับรองแล้วพิมพ์จากรายการจ่ายที่เภสัชกรกรอกและยืนยัน ไม่ใช้ AI แปลงคำตอบเป็นคำสั่งยา ต้องตรวจฉลากจริงกับเครื่องพิมพ์และขนาดกระดาษที่จะใช้

## ข้อผิดพลาดที่พบบ่อย

| ข้อความ | วิธีตรวจ |
| --- | --- |
| Frontend/backend คนละรุ่น | URL ชี้ deployment เดิม หรือยังไม่ได้ deploy เวอร์ชันใหม่ |
| AUTH | รหัสผู้ใช้ กุญแจ hash และ active ใน USERS_JSON |
| AUDIT_UNAVAILABLE | Spreadsheet ID / สิทธิ์บัญชีผู้ deploy / quota Sheets |
| UPSTREAM_CONFIG | คีย์ โมเดล สิทธิ์โครงการ และรูปแบบ Gemini API |
| UPSTREAM_QUOTA | quota/billing ในโครงการ Gemini ไม่มีการ retry อัตโนมัติ |
| INCOMPLETE_RESPONSE | คำตอบถูกตัดหรือบล็อก ระบบไม่แสดงเป็นผลสมบูรณ์ |
| PENDING | งานเดิมยังทำ ให้รอแล้วรับผลเดิม ไม่กดสร้างงานซ้ำ |
| EXPIRED_REQUEST | cache ผลหาย/หมดอายุ ให้ตรวจ audit ก่อนเริ่มใหม่ |
| ติดต่อบริการไม่ได้ / ไม่ได้ส่ง JSON | `/exec`, การตั้งสิทธิ์, redirect, นโยบาย Workspace และ CORS ต้องทดสอบบน browser จริง |
